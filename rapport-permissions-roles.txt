1. ARCHITECTURE GLOBALE
================================================================================

Le systeme repose sur un modele RBAC (Role-Based Access Control) avec :
- Des PERMISSIONS granulaires (400+) definies comme constantes statiques
- Des ROLES qui regroupent des permissions (geres cote backend via API REST)
- Un JWT qui transporte les permissions de l'utilisateur dans le claim "auth"
- Une verification cote frontend via directive Angular et guards

FLUX D'AUTHENTIFICATION :
  1. POST /api/auth/signIn avec {login, password}
  2. Le backend retourne un JWT contenant :
     - sub : username
     - auth : permissions separees par des virgules (ex: "READ_AGENT,ADD_AGENT")
     - exp : timestamp d'expiration
     - IdUser : identifiant utilisateur
  3. Le token est stocke en sessionStorage
  4. Les permissions sont decodees et stockees en sessionStorage

2. DEFINITION DES PERMISSIONS (Authority.ts)
================================================================================

Les permissions sont des constantes de type string, organisees par module.
Convention de nommage : ACTION_ENTITE ou ACTION_SOUS_ENTITE

ACTIONS POSSIBLES :
  - READ_    : Lecture/consultation
  - ADD_     : Creation
  - EDIT_    : Modification
  - DELETE_  : Suppression
  - EXPORT_  : Export de donnees
  - IMPORT_  : Import de donnees
  - GENERATE_: Generation de documents
  - VALIDATION_ : Validation/approbation
  - ARCHIVER_   : Archivage
  - CHANGER_STATUT_ : Changement de statut

PERMISSIONS SPECIALES :
  - ALL_ACCESS  : Acces total (super admin) - bypass toutes les verifications
  - ROOT_ADMIN  : Administrateur racine

3. STRUCTURE DU JWT (Token)
================================================================================

Payload du JWT decode :
{
  "sub": "admin@dgpsn.sn",        // Username
  "auth": "READ_AGENT,ADD_AGENT,ALL_ACCESS,...",  // Permissions (virgule-separees)
  "exp": 1713052800,               // Expiration (timestamp Unix en secondes)
  "IdUser": 1                      // ID utilisateur
}

Verification expiration :
  token.exp > Math.floor(Date.now() / 1000)

5. LOGIQUE DE VERIFICATION DES PERMISSIONS
================================================================================

A. VERIFICATION DANS LES TEMPLATES (Frontend - a reproduire cote backend)
------------------------------------------------------------------------

La directive *afHasAnyAuthority verifie si l'utilisateur possede AU MOINS
UNE des permissions requises (logique OR) :

  Algorithme :
  1. Recuperer les permissions utilisateur depuis sessionStorage
  2. Pour chaque permission requise, verifier :
     - L'utilisateur possede cette permission exacte
     - OU l'utilisateur possede "ALL_ACCESS" (bypass total)
  3. Si au moins une permission match -> AUTORISE
  4. Sinon -> REFUSE (element masque)

  Pseudo-code :
  function hasAnyAuthority(requiredPermissions: string[]): boolean {
    const userPermissions = getUserPermissions();  // depuis le JWT
    return requiredPermissions.some(required =>
      userPermissions.includes(required) ||
      userPermissions.includes('ALL_ACCESS')
    );
  }

B. PROTECTION DES ROUTES (Guard)
---------------------------------

Le AuthGuard actuel verifie uniquement si l'utilisateur est connecte
(pas de verification de permissions specifiques par route).

  canActivate():
    if localStorage.isLoggedin exists -> AUTORISE
    else -> REDIRIGER vers /auth/login

C. INTERCEPTEUR HTTP
---------------------

L'intercepteur ajoute le token JWT a chaque requete sortante :
  - Header: Authorization: Bearer <token>
  - Exclut les URLs publiques : /signIn, /login, /public
  - Gere les erreurs :
    - 401 : Session invalide -> deconnexion + redirection login
    - Token expire : deconnexion + redirection login

6. GUIDE D'IMPLEMENTATION NESTJS
================================================================================

Pour reproduire ce systeme dans NestJS, voici l'architecture recommandee :

A. ENTITES (TypeORM/Prisma)
----------------------------

  // permission.entity.ts
  Permission {
    id: number
    code: string          // ex: "READ_AGENT"
    label: string         // ex: "Lire les agents"
    module: string        // ex: "ACTES_GESTION"
    feature: string       // ex: "AGENT"
  }

  // role.entity.ts
  Role {
    id: number
    code: string
    libelle: string
    permissions: Permission[]  // ManyToMany
  }

  // user.entity.ts
  User {
    id: number
    login: string
    password: string       // hash bcrypt
    roles: Role[]          // ManyToMany
    // ou
    profile: Profile       // ManyToOne -> Profile -> Roles
  }

B. AUTH MODULE
--------------

  // auth.service.ts
  signIn(login, password):
    1. Trouver l'utilisateur par login
    2. Verifier le mot de passe (bcrypt.compare)
    3. Collecter toutes les permissions via les roles
    4. Generer le JWT avec :
       {
         sub: user.login,
         auth: permissions.map(p => p.code).join(','),
         IdUser: user.id
       }

  // jwt.strategy.ts (Passport)
  validate(payload):
    return {
      userId: payload.IdUser,
      username: payload.sub,
      permissions: payload.auth.split(',')
    }

C. GUARDS DE PERMISSIONS
--------------------------

  // permissions.guard.ts
  @Injectable()
  export class PermissionsGuard implements CanActivate {
    canActivate(context: ExecutionContext): boolean {
      const requiredPermissions = this.reflector.get<string[]>(
        'permissions', context.getHandler()
      );
      if (!requiredPermissions) return true;

      const { user } = context.switchToHttp().getRequest();
      return requiredPermissions.some(permission =>
        user.permissions.includes(permission) ||
        user.permissions.includes('ALL_ACCESS')
      );
    }
  }

D. DECORATEUR DE PERMISSIONS
------------------------------

  // permissions.decorator.ts
  export const RequirePermissions = (...permissions: string[]) =>
    SetMetadata('permissions', permissions);

  // Utilisation dans un controller :
  @RequirePermissions('READ_AGENT', 'ALL_ACCESS')
  @Get('agents')
  findAll() { ... }

7. POINTS IMPORTANTS POUR LA MIGRATION
================================================================================

1. Le claim JWT "auth" contient les permissions en chaine separee par des
   virgules. Le backend doit generer ce format exact pour la compatibilite
   avec le frontend existant.

2. La permission "ALL_ACCESS" agit comme un super-admin bypass. Toute
   verification de permission doit aussi verifier ALL_ACCESS.

3. Les permissions sont granulaires (CRUD par entite). Un role est
   simplement un groupement de permissions.

4. Le frontend ne verifie PAS les permissions par route (uniquement
   login/pas login). La securite reelle DOIT etre cote backend avec
   les guards NestJS.

5. Les endpoints API doivent suivre le meme schema d'URL que le frontend
   attend (voir section 4).

6. Le token expire et le frontend gere la deconnexion automatique.
   Le backend doit configurer un TTL coherent sur le JWT.

7. Les modules de permissions sont : DASHBOARD, ACTES_GESTION,
   PROJECT_LIST, BUDGET, COURRIER, GED, SECURITE, REFERENTIEL.
